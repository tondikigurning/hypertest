# Automation

The scenario explorer is an early implementation of [SPEC.md](./SPEC.md). From the repository root, run `pnpm --filter automation dev` and open `http://localhost:3110/automation/`. This starts Vite and a separate Express API on loopback port 3111; Vite proxies API requests to it. Both ports must be available. Scenario definitions come from the BDD feature files and environment-specific results come from PostgreSQL. Development and production builds generate the same feature snapshot.

The local runner stores latest results by environment and scenario using Drizzle and PostgreSQL. For a fresh local setup, run `docker compose -f apps/automation/compose.yaml up -d` from the repository root, then `pnpm --filter automation db:migrate`. The default development connection uses `127.0.0.1:55432`, database and user `automation`, and the local-only password `automation`. Set `AUTOMATION_DATABASE_URL` in the API and migration process environments to use a different database. Do not use the development credentials for a shared deployment. Drizzle migrations live in `drizzle/`; generate new ones with `pnpm --filter automation db:generate`. Existing unscoped results are not imported because their environment is unknown. The static build snapshot has no environment-specific results.

Direct `pnpm --filter tenants test:bdd` can opt into the same storage by setting both `AUTOMATION_ENVIRONMENT_ID` (the matching Automation environment ID) and `AUTOMATION_DATABASE_URL`. Without the environment ID, the existing unscoped BDD workflow continues. Run results awaiting a database write are retained under `.cache/automation-results-pending` and retried at the next Automation server start or BDD import against the same database. A process crash before the Playwright result file is written still requires a rerun.

## Source layout

`src/main.tsx` starts React and loads the shared styles and Hyperscal icon set. `src/app` composes the explorer, while `src/features/scenarios`, `src/features/runs`, `src/features/evidence`, and `src/features/agent` hold their respective logic and feature-specific UI. `src/components/index.ts` is the registry for UI shared across features: `Modal`, `CloseButton`, `CollapsibleRegion`, `FilterSelect`, `Spinner`, and `RetryButton`. Use these for the same interactions; keep scenario, run, evidence and agent behavior in their feature folders. `FilterSelect` uses the same Radix select primitive as `@hyperscal/ui` without importing its full root bundle. Buttons and loading treatments retain their small app-specific implementations, and the native dialog keeps this preview's focus and close behavior.

Shared visual assets and the global stylesheet live in `src/assets` and `src/styles`. The stylesheet remains global because its existing selectors and overrides depend on their order. The `server` directory contains the local Express API, catalog and runner modules, with their Node tests beside them. The API is a local development service, not the hosted backend described in the specification.

The server uses feature-oriented modules with a small composition root:

```text
server/
  app.mjs                   # Compose routers and HTTP middleware
  server.mjs                # Bind the development server to loopback
  middleware/               # Shared HTTP error and not-found handlers
  modules/
    catalog/                # Catalog routes, controller and parsing
    runs/                   # Run routes, controller, service, selection and progress
    evidence/               # Evidence routes, controller and Drive client
    agent/                  # Local agent routes, Codex session and workspace review
  shared/                   # Local request checks used by multiple features
  app.test.mjs              # HTTP integration tests for the composed app
```

Feature-specific tests live alongside their modules. Each feature's routes register endpoints, while its controller handles HTTP requests and responses. The catalog parser is also used by the Vite build, so it remains independent of Express. The run controller validates requests and serves artifacts; the run service owns the in-memory run and subprocess lifecycle. Selection validation and progress reduction remain separate pure modules. The evidence controller resolves scenario folders and controls responses, while the Drive client handles authentication, file listing and downloads. Keep new feature-specific behavior within its feature, and put shared infrastructure at the server level only when it is actually shared. Express routers provide the HTTP boundaries; see the [Express router documentation](https://expressjs.com/en/guide/using-middleware.html#middleware.router). This organization follows the component-oriented approach described in [Node.js Best Practices](https://github.com/goldbergyoni/nodebestpractices#1-project-architecture-practices) without adding unnecessary layers to this local service.

The service runs on the machine that starts it. Hosted API, authentication, persistent queue, worker deployment and environment-specific storage are future integration points; there are no deployable hosted defaults or credentials in this preview.

The Automation home at `/automation` opens the QA Agent. Use the collapsible left sidebar to browse modules and open a feature at an extension-free `/automation/features/<route-key>` URL. Feature routes can be bookmarked and reopened; older feature paths and `module` and `submodule` query links are redirected when their feature is available. Unknown paths return to the Automation home. The agent remains available as a widget while browsing and keeps the same conversation when returning home.

## QA Agent preview

The QA Agent widget connects to a locally installed, authenticated Codex app-server. Choose `ask-qa`, `write-e2e-scenarios`, or `write-e2e-code` from **Skills** when needed. The skill chip clears after sending, while follow-up messages continue the last selected skill; a new chat defaults to `ask-qa`. Press Enter to send or Ctrl+Enter (Command+Enter on macOS) for a new line. Use **Stop agent** to interrupt an active turn. The composer shows the selected QA skill and attached context as removable chips. Context remains in the composer for follow-up messages until removed or cleared, and is copied into each submitted user message. Start from the current explorer selection or use **Add context** to attach a menu, category, or scenario. On the home page only menus are offered; within a menu, categories correspond to the explorer's groups such as Create and include only that category's scenarios. Attachments can be replaced or removed. The picker allows up to eight items and the server caps combined resolved context at 64 KB. Context in the browser is local to this preview and shared across its tabs. Use **Attach file** to add images (PNG, JPEG, GIF, WebP), PDF, DOCX, XLSX, or UTF-8 text files to the next message. Each file is limited to 4 MB and all files together to 8 MB; extracted text shares the 64 KB context limit. PDF files need selectable text (scanned PDFs require OCR), and legacy DOC/XLS files must be converted to DOCX/XLSX. Images are sent to Codex as images; document and spreadsheet text is extracted. Attachments are cleared from the composer after sending; do not attach credentials. Context labels in the transcript show what was attached; they do not prove that a model followed every skill instruction.

New sessions use the destination repository's current committed `HEAD` and create a detached Git worktree under `.cache/automation-agent/workspaces`; uncommitted changes and ignored files from the main checkout are not included. A local branch is created when reviewed changes are committed. Existing sessions keep their original base and branch. Dependencies are linked from the local checkout and remain outside the agent's writable workspace. Attached scenario and feature identities are resolved against that committed workspace; stale or ambiguous selections are rejected. Align the source and catalog through the normal Git and generation workflow, then start a new chat based on the appropriate commit. The agent requests a workspace-write sandbox with network access for browser exploration and can create or edit files there. The selected top-bar environment is passed to each agent message as the exploration target. Use **Review changes** to inspect tracked and new files and explicitly commit the reviewed version to the local branch; a changed diff must be reviewed again. Binary changes appear as Git binary patches; inspect their contents with suitable local tools before approving a commit. Pull request submission is temporarily disabled; the preview does not push or create PRs.

The review panel also previews scenarios from changed feature files; it shows the full changed feature, including scenarios that did not change. When scenario changes are not yet approved, the panel blocks their approval if the draft also contains E2E implementation changes. Preserve those implementation changes separately and remove them from the draft before reviewing the scenarios; after approval they can be restored for further review. This conservative check also applies to unrelated implementation edits in the same draft. A draft belongs to the agent worktree and does not update the explorer's catalog. Committing that worktree does not update the current checkout, regenerate its catalog, or redeploy Automation. To integrate it, inspect `git worktree list`, review the branch and commit, and use the team's normal Git workflow. Do not hand-edit generated catalogs.

Codex command and file approval requests appear in the widget. They are distinct from QA review: when a workspace contains changed `.feature` or `.flows.md` files, **Approve reviewed scenario changes** records approval for their current content. The preview refuses to start an explicit `/write-e2e-code` turn or commit those scenario changes if their content differs from the approved snapshot. This does not enforce every skill instruction: automatic specialist handoffs, flow-list review, historic scenario approval and data-safety rules still depend on the agent and user.

Changed draft scenarios are overlaid in the current preview user?s explorer, with new, changed and deleted labels. Draft execution and Finalize are temporarily disabled while the workflow is being verified; the QA Agent does not run its draft scenarios. Use the explorer's local runner for scenarios available in the current checkout; its result does not verify unmerged changes in the agent worktree. The agent must report draft verification as not run unless it has actual runner evidence.

The conversation and worktree reference are stored locally in `.cache/automation-agent/session.json` so an interrupted session can be resumed; Codex also keeps its own thread state. A workspace is retained even if Codex fails to start. Pending tool requests do not survive a server restart; the widget reports the interruption and asks the user to request the question or permission again. Never send credentials through chat or a custom note. If Codex marks a question as secret, the widget offers a safe continue action and sends only a credential-withheld message. For write-e2e-scenarios, Variables and the selected environment are also sent to the local API to prepare a named authenticated playwright-cli session. The agent receives the session name and target, not the credential values. Login state is written to a private temporary directory only for transfer and removed afterwards; the authenticated browser remains sensitive and is closed on a new chat or environment/account change. A browser may outlive the API after a crash until its CLI idle timeout. Set Variables in the same tab before sending the scenario request. If login fails, check Variables and target access, then retry; do not send credentials in chat. The frontend assigns a persistent dummy preview identity per browser profile; its agent conversation is shared by tabs in that profile and isolated from other dummy identities. This is not authentication or a security boundary, and other local API features still use shared state. The earlier unscoped conversation remains in its existing session file but is not opened automatically by the dummy-identity UI. Worktrees and branches are retained after a new chat or restart; inspect them with `git worktree list` and remove them with Git when no longer needed. Codex, Git, Git author identity and model access must be configured on the local machine. This remains a local preview, not a hosted agent service.

## Architecture and contribution rules

Coding agents and contributors should also follow the app-scoped [AGENTS.md](./AGENTS.md).

- Keep `src/app` responsible for composing the screen and coordinating navigation. Put scenario filtering and grouping in `features/scenarios/selectors.ts`; keep these functions independent of React and browser APIs.
- Keep network lifecycle and cancellation in feature hooks or services. `use-scenario-catalog.ts` owns catalog loading, the static snapshot fallback, and refresh after a completed run. Avoid fetching the same resource directly from presentation components when a feature already owns it.
- Keep reusable UI primitives in `src/components` and domain-specific UI and types in their feature. Preserve scenario keys and IDs when presenting or selecting scenarios; IDs can be missing or duplicated in source data.
- Treat the local server as a development-only boundary. Validate selections on the server, keep credentials and local paths out of public output, and do not enable hosted execution without the controls described in the specification.
- Follow the repository's Biome rules and TypeScript strict mode. Explain narrowly scoped suppressions where source data or an intentional browser fallback makes a rule inappropriate. Preserve the global stylesheet's cascade when changing it.
- For behavior changes, verify the affected workflow and add appropriate coverage using the repository's testing conventions. Do not edit generated scenario catalogs by hand.

From the repository root, check formatting and lint with `pnpm exec biome check apps/automation`, and check the app with `pnpm --filter automation typecheck`, `pnpm --filter automation build`, and `node --test 'apps/automation/server/**/*.test.mjs'`. The server tests do not start BDD scenarios.

## Local execution

Choose DEV, STT, STT1, or PP in the top bar before running. STT1 is selected initially. The server's `BASE_URL` (or the tenants `.env.local` value) remains available as a configured target if it does not match a listed environment. The target is fixed while a run is active. Drive evidence is stored per run under `E2E Evidence/<environment>/<app>/<feature path>/<scenario ID>/<run ID>/`; the viewer shows only the latest uploaded run. Existing unscoped evidence is left in place and is not shown as belonging to any environment. Automation reads environment-specific results from PostgreSQL; existing Markdown results remain unscoped.

Runner preparation is cached in memory for the API process lifetime. After a successful generation, unchanged BDD sources, configuration, dependency lockfile, test-utils sources and generated output reuse that generation. Playwright discovery is scoped to the selected feature files and cached for up to 32 feature selections; every request still checks its IDs against the collected tests before execution. Changing tracked runner inputs or generated files invalidates both caches. The first run after an API restart still performs generation and collection. Authentication, execution and evidence upload happen for each run.

Progress polling consumes only newly appended reporter events. Browser preview polling runs independently from the progress panel, pauses downloads in hidden tabs, and checks frame validators before downloading another JPEG. Frames are decoded before display to reduce flicker; the preview remains view-only and best effort.

The development server offers local execution of a scenario, a whole feature, or a category within a feature. Set required environment variables in the top bar before running. Values remain in the current browser tab session; add future required variables to the runner controller variable definitions. Runs use the selected target (default STT1). The target is displayed before submission. Feature and category runs include the entire selected group regardless of search and filters. The local service resolves IDs from the server catalogs, runs BDD generation, checks Playwright collection by exact scenario ID, and executes the matching projects. If a group contains missing, ambiguous, or unregistered IDs, or the feature and catalog disagree, the run stops rather than executing only part of the selection. A live panel shows the Chromium browser as periodically refreshed frames and reports Playwright steps as they execute; it is a view-only preview, not an interactive browser. It also displays locally produced screenshots and videos for each scenario, and removes its temporary authentication state after the process finishes. Artifacts remain in a temporary directory on the local machine. The most recent run is retained only in server memory and is lost when the development server restarts. Do not run local/CI BDD generation concurrently with this preview because generated test files are shared.

An active run's preview can be reopened from the floating run indicator after closing it. Once a run finishes, the app does not offer a way to reopen or view it as run history. If the preview stayed open while the run was active, it shows that run's final progress before it is closed. The preview can fill the app window. Cancelling stops the active local process; on Windows this forcibly stops its process tree, so the current scenario and its cleanup may be interrupted. This local behavior does not implement the draft hosted runner's graceful, after-scenario cancellation.

The app itself does not require sign-in for this local preview. Execution is available only on the loopback development server, one run at a time. It does not enforce scenario data-safety approvals; the existing suite and its test data must be maintained accordingly. Each run saves its latest results to PostgreSQL and uploads its available screenshots/videos to the selected environment's Drive folder using the same optional credentials as `pnpm test:bdd`. Automation runs do not update the generated Markdown catalogs; other BDD workflows continue to maintain them. Missing Drive configuration is shown as unavailable in the run view; upload failures are shown separately from test outcomes. Do not expose or deploy this preview: it does not implement access control, a durable queue, or the remaining specification. The development catalog endpoint reads feature files from the local checkout; a built app uses the generated catalog snapshot and has no runner API.

Scenario details include source tags, steps, outline examples and references. A reference opens its scenario when exactly one matching ID exists in the catalog; external references, missing IDs and duplicate IDs are left unresolved. The explorer marks scenarios without a unique stable ID and outlines without examples unavailable for selection. Other execution availability remains unknown until runner registration and bindings can be verified; these discovery checks do not authorize execution.

The hosted runner needs an authenticated session handoff that accounts for Hyperscal's rotating refresh tokens, environment-isolated storage and Drive evidence, shared-data approval enforcement, and a durable cross-instance queue before execution can be enabled safely. Existing `pnpm test:bdd` uses separate configured credentials and shared output paths; it must not be exposed directly as a web endpoint.

The BDD configuration has opt-in integration points for a future trusted worker. `AUTOMATION_STORAGE_STATE` is an absolute path to a Playwright storage-state file and disables the normal setup dependency for authenticated projects. `AUTOMATION_OUTPUT_DIR` and `AUTOMATION_REPORT_DIR` isolate artifacts, and an absolute `AUTOMATION_EVENTS_FILE` enables the Automation reporter's JSONL events. An absolute `BDD_RESULTS_FILE` keeps the shared result reporter's JSON separate per run while it updates only catalogs for covered features. The reporter preserves the Playwright test ID for each outline example. These options do not provide session delegation, a queue, access control, or hosted evidence access; storage-state files contain secrets and need secure, short-lived handling. Do not enable these options for untrusted requests.

`server/modules/runs/run-progress.mjs` reduces local reporter events into per-example and per-step progress and marks unfinished work interrupted when a worker exits unexpectedly. The local API exposes only selected progress fields. Reporter events can include local paths and failure messages and must not be exposed to viewers without access controls and sanitization.
