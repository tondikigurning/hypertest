# Write E2E Code (Phase 1)

For both terminal agents and Q-Rex, implement all scenarios in the requested scope that lack complete code and are eligible for implementation, including scenarios from multiple approved batches, as reusable steps, page/component objects, fixtures and reviewed mocks. Continue across batches in the same turn; do not stop after the first batch or impose a scenario-count limit. Read the [shared workflow contract](../ask-qa/references/workflow-contract.md) for host-specific approval, scope, completion evidence, external verification handoff and the **question boundary**. Whenever you ask the user a question, stop the turn immediately after presenting it and wait for the answer before doing any more work. Use [E2E conventions](../write-e2e-scenarios/references/e2e-conventions.md) and [data safety](../write-e2e-scenarios/references/data-safety.md) for identity and test data.

For new/changed intent, verify approval of the **current** feature snapshot and exact scenario IDs before implementation. In a terminal, record or recover the actual explicit decision using the [terminal scenario review record](../write-e2e-scenarios/references/flow-registry.md#terminal-scenario-review-record); a matching record can survive a new session. In Q-Rex, chat approval is insufficient: use the actual Changes-panel decision or configured automatic mode. Existing implemented scenarios can receive intent-preserving technical repairs/refactors without a new scenario-design gate; preserve their contract and IDs and inspect data safety.

An unchanged scenario already present in the workspace's committed baseline can be implemented without a new scenario-design approval when its existing contract is clear, even if it has no bindings or historical review record. Compare the actual scenario and inherited tags/background/examples with the baseline, using the host's available source and diff evidence; a catalog entry or absent review record alone does not establish baseline status. Treat its historical review as unknown, not approved. Preserve its intent and IDs; investigate missing implementation evidence, and route ambiguous or changed intent through scenario review instead of guessing. This eligibility does not override a host-wide write block or live-data rules.

Preserve the requested module/menu. Resolve feature candidates by contents and product evidence, not sibling proximity. If the target has no matching scenario, or its intent needs to change, apply [write-e2e-scenarios](../write-e2e-scenarios/SKILL.md) yourself for that target, including its PRD/discovery/review prerequisites. A host write block alone does not mean the scenario is missing. Reuse context; ask only when target or approval remains materially ambiguous. Do not ask the user to pick an unrelated feature or invoke the handoff again.

## Step 0 — Resolve eligible scope

Before any browser call, apply [exploration reuse](../ask-qa/references/exploration-context.md) when that reference exists in the current workspace. Recover the menu's shared `.exploration.md`, including PRD-phase evidence, and the available conversation and scenario handoff. Use `.exploration.md` for detailed browser facts, scenario mappings and reviews; use `.flows.md` only for the confirmed inventory and gaps. Missing handoff evidence need not mean the browser fact is missing. If the reference or record is unavailable, report it, reuse applicable evidence from accessible context and investigate only remaining gaps; do not claim the missing material was read.

Inventory every scenario in the requested scope across its relevant feature files, including all applicable batches. Identify each scenario by source path and ID (or location when missing or duplicated), its baseline or current approval status, and whether existing bindings, registered paths, fixtures and supporting code fully implement its contract. A matching step name or catalog entry alone does not establish complete implementation. Reuse complete code; implement missing or partial bindings and supporting code for every eligible scenario. Record scenarios blocked by approval, evidence or access and continue independent eligible work where the host permits it. Do not expand a narrower explicitly requested scope.

Group eligible scenarios by shared setup and transitions using the handoff and existing helpers. Identify a representative eligible scenario that exercises each high-impact shared path and an important different branch, with its actual prerequisites and observable outcome. Use this to order implementation and early validation; retain the complete requested scope and every scenario's assertion. Shared setup is not a dependency on another scenario's execution.

In Q-Rex manual mode, an unapproved changed-feature snapshot anywhere in the draft blocks activation of this skill and E2E implementation writes for the whole workspace, including otherwise eligible baseline scenarios. Inspect the current Changes snapshot before implementation. If it needs review and no implementation edits block review, present it through the scenario workflow's native review gate and stop; after approval, resume all eligible work. If implementation edits already block review, preserve them and use the supported separate scenario-only draft workflow or finish the currently approved scope where the host permits; report the exact blocker and next action. Never reset or move existing work implicitly. The shared contract explains the cumulative snapshot and automatic mode.

Recover the scenario phase's relevant conversation and review output when available, and read the owning menu's `.exploration.md` scenario handoff, PRD, `.flows.md` and feature contents from the current workspace. The `.flows.md` contains only confirmed flows and gaps. A new session may have the records without the previous chat. Compare the handoff's scenario contract or exact snapshot identity and PRD reference with current sources, and assess browser evidence separately as directed in [flow registry](../write-e2e-scenarios/references/flow-registry.md#implementation-handoff); an incomplete comparison is unverified, not a match. Reuse applicable mapping, observations, verified locators, request evidence, decisions and gaps. If the handoff, comparison or mapping is unavailable, reconstruct affected links from accessible PRD, approved scenarios or the existing repair contract, report uncertainty, and investigate only remaining gaps. A separate worktree does not automatically contain another draft's artifacts. Do not repeat discovery merely because the skill, turn or session changed. A missing mapping or PRD does not create a new scenario-design gate for an intent-preserving repair. If changed PRD context changes the intended behavior, route the affected scope through scenario review before changing its contract. Establish environment, prerequisites, owned-data scope, cleanup and unresolved product decisions under the shared contract. Report each batch's implementation and verification independently; when execution is unavailable, produce the concrete handoff below.

## Step 1 — Read before writing

1. Read every relevant feature in the requested scope and the owning menu's flat/nested features. Follow [test organization](../../../docs/automation/test-organization.md): children share one parent PRD and ID namespace. Preserve IDs, `@flow:`, `@ref:`, assertions and intent; splits retain inherited tags, backgrounds/examples, safety notes and flow order. Missing requirements belong in a refresh/review of that parent through `write-prd`.
2. Read relevant shared fixtures/utilities, `steps/_shared/`, components and the existing module's steps/POMs and callers. Reuse their style and bindings. Read each linked `@ref:TEN_COM_*` master: its step text is the contract.
3. Inspect actual mock contracts before applying [MSW guidance](references/msw-mocking.md). Consult [troubleshooting](references/troubleshooting.md) only for a matching symptom; do not copy known weak assertions merely because they exist.

## Step 2 — Verify locators

For each locator and interaction needed by the eligible scoped scenarios, first assess available scenario-phase evidence and existing verified code against the target environment, page, role/state and current scope. Reuse evidence that identifies the actual locator and remains applicable; prior verified roles, labels, test IDs and generated locators can support implementation without reopening the browser. A scenario outcome, feature text or bare temporary `eNN` ref alone does not verify a locator. If evidence is missing, ambiguous, inaccessible, stale or contradicted by a relevant UI/environment change, investigate only the affected locator, interaction or branch using the [host's browser capabilities](../write-e2e-scenarios/references/playwright-cli-exploration.md) and data-safety rules. Use a current snapshot and supported inspection or `generate-locator`; refresh temporary refs after navigation or material changes. Q-Rex has no `eval`/`run-code` or element-attribute command. Use verified alternatives and mark remaining gaps instead of inventing locators.

If live access is missing, use applicable prior evidence and preserve usable existing verified code; complete independent work. Report locator-dependent implementation as incomplete where evidence cannot be established. Prior exploration is neither scenario approval nor permission for a new live mutation; apply the actual host decision and current scoped data authorization separately.

## Step 3 — Align scoped data values

Apply the single [test-data convention](../write-e2e-scenarios/references/data-safety.md#test-data-values), including readable names, minute stamps, plain free text and collision handling. Inspect step/POM files in scope, including those being extended, and align violating values in the same pass using the existing helper. Preserve scenario assertions/intent and avoid unrelated module sweeps. Report aligned files/fields.

Data eligibility does not grant mutation permission. Preserve exact target identity through each action; a successful generic search or arbitrary first row does not establish ownership. Missing owned data follows search → supported provisioning → scoped exception review → skip without approval. Inspect notification/downstream effects and restoration limits before any approved exception.

## Step 4 — Implement the existing or reviewed contract

Implement the representative shared paths first and use Step 5 as soon as each is ready, where the host permits. Return here to complete all remaining eligible scenarios; early checks do not reduce scope or replace final validation.

- Steps delegate to POMs/COMs: `Given` establishes prerequisites, `When` acts, `Then` asserts. Put assertions in Then steps or POM `expect*` methods; COMs own shared UI interaction. Shared step text belongs in `steps/_shared/`, not `steps/_components/`.
- Reuse shared/stateful components and register injectable POMs/COMs in `fixtures/base.fixture.ts`. Extend existing classes without breaking their other callers.
- Implement consumer-visible journeys and consequential branches from eligible baseline or approved scenarios, including any explicitly reviewed field or validation behavior. Route missing journeys or changed intent through `write-e2e-scenarios` with the same scope and prior answers, stopping at its applicable review gate.
- Use actual request evidence for reviewed `@mock` handlers. Mocks verify the promised UI contract, not real backend integration. Preserve the no-mock smoke rule.
- Assert the scenario's observable outcome on the identified target. Feedback/network evidence can supplement it; do not substitute a mocked HTTP status for visible UI feedback or silently strengthen/change an assertion. Report a contract gap for scenario review.
- Keep cleanup and target guards effective after failures wherever feasible. A previous approval comment is not current-session seed authorization.

## Step 5 — Validate with available capabilities

Validate incrementally as representative paths become implemented, then complete and verify the remaining eligible scope. First perform feasible non-live binding, collection and type checks for the current source where supported. When execution is authorized and safe, run a narrowly selected representative path and consequential alternate early enough to expose shared setup, locator, interaction or readiness failures before implementing the rest of a large batch. Review the first failure's full available diagnostics and exact failing phase before applying a fix across callers; a timeout or failed visibility check alone does not establish its cause. Keep the exact selection, source snapshot, environment and outcome; a partial pass never verifies the batch. If the host or data rules prevent an early run, continue independent implementation and hand off the specific pending check. In Q-Rex, finish required scenario-only reviews before implementation when later review would otherwise be blocked; incremental checks do not bypass the cumulative review gate.

Distinguish a confirmed absent prerequisite from a control or result that has not become ready. Wait for an appropriate observable settled state and verify absence before treating missing data as a skip; a timeout, inaccessible UI or ambiguous locator is an unresolved failure or blocker, not proof of absent data. Preserve actual runner outcomes and report blocked and not-run work separately. Never relax an assertion, add a mock or skip a scenario merely to improve the pass rate.

**Terminal host:** inspect `e2e/package.json`, invoked runner and config before choosing commands. Check affected bindings, collection and types. Register required implementation paths, including split/nested paths, and check collection for the exact eligible scenario selection, including every moved ID. Before live execution inspect selected setup/steps/POMs/tags, establish the intended environment and follow data safety. Verify the exact selection; an unfiltered `pnpm test:bdd` runs the suite and may sync catalog, import results and upload evidence. Do not generate BDD concurrently with the Automation runner, which shares generated files.

**Q-Rex:** inspect source/bindings and finish feasible code. After scenario approval and implementation, `run_draft_scenario` can run one uniquely identified scenario through the isolated Docker runner. Inspect its setup, require E2E-owned data and separate explicit data-safety approval, and use the selected environment and browser Variables. Draft evidence is temporary and never uploaded or reported as official results. Collection and standalone type checks remain unavailable. Keep an approved changed batch `approved` until collection/type evidence exists; an unchanged eligible baseline scenario with unknown historical review stays historically unknown; do not invent an `approved` decision. Identify branch/base, current full Changes snapshot or supplied source revision/diff, files/scenario IDs and their baseline or approval evidence, supported commands for a terminal reviewer, intended selection/environment and all pending checks. The explorer checkout runner cannot validate an unmerged draft.

External results may advance only the matching current source and complete reviewed scope under the shared contract. If live execution is unsafe/unavailable, do feasible non-live work and record the exact unverified branches. No host may treat generation, an empty/partial selection or a successful process alone as a complete pass.

## Step 6 — Report and stop

Report per scenario: relevant PRD requirement, source ID/path, implementation written, locator/binding gaps, collection/types, actual execution and evidence source. Advance batch evidence to `implemented` only after bindings and collection/type checks succeed; advance to `verified` only after every required scenario passes in the intended environment. Record failures, skips, quarantine, mocks and unavailable checks separately. Preserve the prior batch evidence state when evidence is incomplete; the flow registry tracks authoring, not execution.

Before stopping, save new or corrected locator, request and interaction evidence and blockers in the shared `.exploration.md`, preserving original dates for reused facts. List material files, reused/added steps/POMs/COMs, fixture/mock wiring, data-value alignment and commands actually run or still required. Identify reused PRD/scenario/code evidence and any newly investigated or unresolved gaps, with the record path and evidence IDs where available. Distinguish mocked UI coverage from real backend coverage. Do not change scenario intent in this phase.

After completing all feasible eligible work in scope, end the turn with per-batch results or a concrete external-check handoff. Identify every remaining scenario, its blocker and next action; unavailable checks remain pending and never imply a pass. In Q-Rex, implementation changes can block review of additional scenario edits, so plan scenario-only batches first. Do not add another approval question merely to report an unavailable check.
