# Menu flow registry

Keep one `e2e/tests/bdd/features/<module>/<menu>.flows.md` beside the menu's flat feature or folder. This file contains exactly two sections: `Flows` and `Gaps`. The registry is a Git workspace file; the menu PRD remains in the database. Use paths relative to `e2e/tests/bdd/features/` in the Feature column. Use one row for every confirmed in-scope flow, including later scenario batches; list all feature paths if a flow spans files. Record each discovered candidate awaiting confirmation or further evidence individually under Gaps, with its goal, evidence or limitation and next action. A scenario batch does not limit this inventory. Follow [flow-registry-template.md](flow-registry-template.md) whenever creating or updating the registry.

The Flows table is the confirmed inventory for the whole requested scope, regardless of scenario batching. Keep Gaps only while there are unrepresented requirements, unconfirmed candidates, deferred or blocked branches, or other material limitations. Keep confirmation provenance and each authored batch's implementation handoff in the menu's `.exploration.md`, not in `.flows.md`.

Before confirmation, list proposed candidates under Gaps and leave the Flows table without confirmed rows. In a terminal, keep the pending comparison in `.exploration.md`; add flow rows only after the explicit decision. Q-Rex uses its native flow decision rather than a Markdown confirmation record. A scenario handoff is required once a batch is authored, not for every pending flow.

`pending` means the confirmed scope is not fully written, including partially written flows. `written` means scenarios for the confirmed scope have been authored, including any `@fixme` scenarios; it does not mean approved, implemented or passed. Reconcile pre-existing scenarios before marking them written. Preserve unrelated rows. If confirmed scope expands or scenarios are removed, return the affected flow to `pending` until its scope is written. Remove rejected or retired flows from the table; preserve existing scenario intent until its own review changes it, and reserve retired IDs in the applicable feature history or review record.

Use Gaps for unrepresented requirements, unconfirmed candidates, important scenarios or branches deferred to later batches, inaccessible roles/data and material limitations; identify the affected flow or requirement, specific remaining branch and next action where known. Remove resolved gaps; omit the section when none remain. Do not put credentials, customer data or sensitive browser evidence in the registry.

## Flow confirmation provenance

Before a terminal flow review, identify the exact described flow IDs and files and record a pending comparison in the menu's `.exploration.md` under `## Flow confirmation provenance`: the SHA-256 of the exact UTF-8 active PRD content and raw bytes of each complete feature file. Record an absent new feature as absent rather than hashing an empty file. Present the inventory and its scope for explicit confirmation. After the user confirms and before authoring, read the active PRD and features again and recompute the comparisons. If any source, described flow or scope changed while awaiting the decision, present the current inventory for a new confirmation. Otherwise record the actual decision/date and available decision reference with those matching sources. A pending record or digest is not a decision. Do not persist PRD contents or sensitive data merely to identify the snapshot. If the registry does not exist, keep the pending comparison in `.exploration.md`; never add a third section to `.flows.md`.

Preserve the confirmed scope while authoring. After the agent's own intended feature changes, verify the active PRD is still the confirmed content and the feature files contain only the expected changes under that confirmed list, then record the new raw-byte feature digests alongside the original confirmation in `.exploration.md`. Describe these as the agent's own changes under the confirmed list, not a new user decision. If the PRD, scope or feature contents changed independently, reconcile them and seek a new confirmation where the decision no longer covers them. Do not silently extend the confirmed inventory.

On a later terminal session, read the active PRD and current exact feature files in the same workspace, recompute these digests and compare the decision, described flows, file paths and current scope recorded in `.exploration.md`. Reuse the actual confirmation only when its recorded post-authoring feature references and active PRD still match and the scope is unchanged. Missing, ambiguous or invalidated decision evidence needs the existing confirmation gate, while still-applicable browser evidence remains reusable. A hash or flow table alone is not evidence of the user's decision. Q-Rex uses its native persisted decision and source checks; a Markdown entry in `.exploration.md` cannot replace them.

## Implementation handoff

For each authored batch, save a concise handoff under `## Scenario handoffs` in the menu's `.exploration.md` before scenario review so a new session can resume without conversation history. Keep separate entries for batches and preserve unrelated entries. Keep `.flows.md` limited to Flows and Gaps.

Use the menu's [shared exploration record](../../ask-qa/references/exploration-context.md) as the canonical detailed browser log from PRD through code. Reference relevant evidence IDs rather than duplicating browser facts. Keep the scenario contract, requirement mapping, batch decisions and terminal review record in the handoff within `.exploration.md`. Existing handoffs with inline browser evidence remain usable; assess and reuse them without requiring a migration or another browser visit.

Each batch entry identifies:

- Exact feature paths and scenario IDs with source locations when identities are missing or duplicated; the owning PRD identifier and its version/content reference when available. Include a safely storable, exact copy of each selected scenario's tags, title, steps and examples and its applicable feature/rule tags and background, or an exact host-provided identity for that feature snapshot. A source revision alone does not identify uncommitted changes. If sensitive content must be omitted, mark that portion uncheckable rather than calling a sanitized excerpt exact.
- The requirement-to-scenario coverage mapping from scenario review, including applicable shared rules and observed branches without a requirement ID. Keep its condition, source or PRD ID, exact feature path and scenario identity, asserted outcome or gap, coverage classification, and reason/next action for unresolved rows. Preserve many-to-many relationships and the scope decisions behind exclusions or deferrals. This is the durable copy of the review summary, not a new PRD or a test result.
- Observation date, target environment, page, role and relevant state; observed outcome and each reusable, actually verified locator expression associated with its interaction or outcome. Record the supported evidence source and UI version or other relevant change indicators when known. A temporary `eNN` ref is not a locator expression.
- Available sanitized request-contract evidence needed for reviewed mocks, prerequisites and cleanup, unresolved product decisions, and blocked or unverified locators/branches with next actions. State when a detail or evidence source is unavailable; never infer a request schema or fabricate an artifact.

Store only safe, minimal facts: no credentials, session state, customer data, sensitive record identities, raw browser snapshots, request bodies/headers, tokens, absolute local filesystem paths or sensitive URLs. Omit or generalize sensitive values while preserving what is necessary to assess applicability; if that makes evidence unusable, record the gap. Record terminal scenario decisions only as described below; do not represent live-data permissions, test results or implementation status as transferable evidence.

When evidence or scope changes, update the affected entry in `.exploration.md` and retain still-applicable entries. Do not invent a digest or describe a partial comparison as an exact match. Compare the saved scenario contract or exact snapshot identity and PRD version/content reference with current sources to assess each mapping row. Separately assess each browser observation and locator against its own evidence, environment, page, role/state and known UI changes; a matching scenario contract does not prove the UI is unchanged. If a PRD reference is missing or a mapping cannot be compared, report the affected mapping as unverified, but retain an independently applicable verified locator. If the scenario, environment or UI changes affect a particular observation, or its own provenance is insufficient, re-investigate only that evidence. Reassess affected mapping rows against the current contract; route any further intent changes through the existing scenario review gate, without repeating a decision that already covers the current snapshot. Reuse unaffected evidence.

The handoff does not itself establish that a scenario snapshot is approved, that evidence remains current, or that a live mutation is authorized. In Q-Rex, the scenario approval digest covers changed `.feature` files, not this registry; even when the full Changes diff included the registry at review time, a later registry edit does not invalidate scenario approval. Treat the mapping and observations as supporting evidence to reconcile, not as independently approved product intent. Follow the host's actual scenario approval and data-safety decisions separately.

On resume, recover the shared exploration record, flow inventory, active menu PRD and relevant features; reconcile their current contents, gaps and available prior confirmation and exploration evidence. Reuse still-applicable discovery, and re-explore only changed or unverified areas and the selected journey's missing detailed evidence. Reuse a still-valid host confirmation when available. If its snapshot or decision is unavailable, report the missing evidence and request the required confirmation for affected files, without repeating unrelated discovery. Reconfirm affected flows if their scope or supporting PRD/feature contents materially changed. The handoff alone does not grant flow, scenario or live-data approval; a valid terminal scenario review record is evidence of a separate explicit decision, not permission for live mutation. Preserve review and batch gates in the shared contract. If the flow inventory or exploration record is absent from the current workspace, do not assume another worktree's draft is available; inspect accessible features, PRD-phase exploration and context and report the missing handoff. Missing scenario handoff metadata does not erase independently applicable browser evidence.

## Terminal scenario review record

For a terminal review of new or changed scenario intent, keep a `### Terminal scenario review` entry in the batch's implementation handoff:

1. Before requesting review, identify the exact batch and each feature path relative to the repository root, with scenario IDs and source locations where IDs are missing or duplicated. Calculate SHA-256 over the raw bytes of each current complete feature file, including uncommitted changes; record each path and digest as a **pending** review. Present the exact feature changes and batch with the request. A Git commit alone may omit working-tree changes; a digest identifies content but is not an approval.
2. End the turn for explicit review under the shared contract. Do not mark pending as accepted because the user requested the work, remained silent or approved flows. If rejected or changed, keep the decision truthful, update the batch and request review of the new content.
3. On the next turn after the user explicitly approves that exact batch, recalculate each file's digest. If paths, identities, batch or any bytes differ, do not record acceptance for the changed files: present the current batch for a new decision. Otherwise record the manual acceptance, the actual date, established reviewer identity if known (otherwise `identity not recorded`), and a reference to the decision if available. Do not invent a reviewer, response or timestamp. Record before beginning implementation or other independent work, and preserve unrelated batch records. If the session ends before the decision is recorded and its evidence cannot be recovered, a new session must request review of the current batch.
4. On a later terminal session, recover the recorded explicit decision, batch and file digests; recompute all digests from the current workspace and check that paths and scenario identities still match. Reuse a matching record without re-asking. A later batch editing the same feature file changes its whole-file digest even if the earlier scenario text is unchanged: present the current affected batch for review and record the new decision. Preserve and reuse unaffected records. Missing, pending, ambiguous or mismatched records do not establish approval; obtain the applicable decision while continuing independent work. A record is an honest account of the manual decision, not cryptographic proof of who approved it, permission to mutate live data, or a test result. Do not claim acceptance from a digest alone.

Use the host's available SHA-256 utility, such as PowerShell `Get-FileHash -Algorithm SHA256 -LiteralPath <feature-path>` or a byte-preserving equivalent. Do not print credentials or unrelated file contents. No commit, reset or change to `.feature` files is required to record the decision.
