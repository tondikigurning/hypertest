# Menu flow registry

Keep one `e2e/tests/bdd/features/<module>/<menu>.flows.md` beside the menu's flat feature or folder. The registry is a Git workspace file; the menu PRD remains in the database. Use paths relative to `e2e/tests/bdd/features/` in the Feature column. Use one row per confirmed flow; list all feature paths if a flow spans files.

```markdown
# Users flows

| Flow | Outcome | Feature | Status |
| --- | --- | --- | --- |
| `TEN_USR_CREATE_FLOW` | User is created and invitation is sent | `user-management/users/create.feature` | pending |
| `TEN_USR_EDIT_FLOW` | User details are updated and saved | `user-management/users/edit.feature` | written |

## Gaps

- Supervisor access unavailable; role-specific permissions remain unverified.
```

`pending` means the confirmed scope is not fully written, including partially written flows. `written` means scenarios for the confirmed scope have been authored, including any `@fixme` scenarios; it does not mean approved, implemented or passed. Reconcile pre-existing scenarios before marking them written. Preserve unrelated rows. If confirmed scope expands or scenarios are removed, return the affected flow to `pending` until its scope is written. Remove rejected or retired flows from the table; preserve existing scenario intent until its own review changes it, and reserve retired IDs in the applicable feature history or review record.

Use Gaps for unrepresented requirements, unconfirmed candidates, important scenarios or branches deferred to later batches, inaccessible roles/data and material limitations; identify the affected flow or requirement, specific remaining branch and next action where known. Remove resolved gaps; omit the section when none remain. Do not put credentials, customer data or sensitive browser evidence in the registry.

## Implementation handoff

For each authored batch, save a concise `## Implementation handoff` section in this same registry before scenario review so a new session can resume without conversation history. Keep separate entries for batches and preserve unrelated entries. Each entry identifies:

- Exact feature paths and scenario IDs with source locations when identities are missing or duplicated; the owning PRD identifier and its version/content reference when available. Include a safely storable, exact copy of each selected scenario's tags, title, steps and examples and its applicable feature/rule tags and background, or an exact host-provided identity for that feature snapshot. A source revision alone does not identify uncommitted changes. If sensitive content must be omitted, mark that portion uncheckable rather than calling a sanitized excerpt exact.
- The requirement-to-scenario coverage mapping from scenario review, including applicable shared rules and observed branches without a requirement ID. Keep its condition, source or PRD ID, exact feature path and scenario identity, asserted outcome or gap, coverage classification, and reason/next action for unresolved rows. Preserve many-to-many relationships and the scope decisions behind exclusions or deferrals. This is the durable copy of the review summary, not a new PRD or a test result.
- Observation date, target environment, page, role and relevant state; observed outcome and each reusable, actually verified locator expression associated with its interaction or outcome. Record the supported evidence source and UI version or other relevant change indicators when known. A temporary `eNN` ref is not a locator expression.
- Available sanitized request-contract evidence needed for reviewed mocks, prerequisites and cleanup, unresolved product decisions, and blocked or unverified locators/branches with next actions. State when a detail or evidence source is unavailable; never infer a request schema or fabricate an artifact.

Store only safe, minimal facts: no credentials, session state, customer data, sensitive record identities, raw browser snapshots, request bodies/headers, tokens, absolute local filesystem paths or sensitive URLs. Omit or generalize sensitive values while preserving what is necessary to assess applicability; if that makes evidence unusable, record the gap. Record terminal scenario decisions only as described below; do not represent live-data permissions, test results or implementation status as transferable evidence.

When evidence or scope changes, update the affected entry and retain still-applicable entries. Do not invent a digest or describe a partial comparison as an exact match. Compare the saved scenario contract or exact snapshot identity and PRD version/content reference with current sources to assess each mapping row. Separately assess each browser observation and locator against its own evidence, environment, page, role/state and known UI changes; a matching scenario contract does not prove the UI is unchanged. If a PRD reference is missing or a mapping cannot be compared, report the affected mapping as unverified, but retain an independently applicable verified locator. If the scenario, environment or UI changes affect a particular observation, or its own provenance is insufficient, re-investigate only that evidence. Reassess affected mapping rows against the current contract; route any further intent changes through the existing scenario review gate, without repeating a decision that already covers the current snapshot. Reuse unaffected evidence.

The handoff does not itself establish that a scenario snapshot is approved, that evidence remains current, or that a live mutation is authorized. In Q-Rex, the scenario approval digest covers changed `.feature` files, not this registry; even when the full Changes diff included the registry at review time, a later registry edit does not invalidate scenario approval. Treat the mapping and observations as supporting evidence to reconcile, not as independently approved product intent. Follow the host's actual scenario approval and data-safety decisions separately.

On resume, read the registry, active menu PRD and relevant feature files; reconcile their current contents, gaps and available prior confirmation and exploration evidence. Reuse still-applicable discovery, and re-explore only changed or unverified areas and the selected journey's missing detailed evidence. Reuse a still-valid host confirmation when available. If its snapshot or decision is unavailable, report the missing evidence and request the required confirmation for affected files, without repeating unrelated discovery. Reconfirm affected flows if their scope or supporting PRD/feature contents materially changed. The handoff alone does not grant flow, scenario or live-data approval; a valid terminal scenario review record is evidence of a separate explicit decision, not permission for live mutation. Preserve review and batch gates in the shared contract. If the registry is absent from the current workspace, do not assume another worktree's draft is available; inspect the accessible features and context and report the missing handoff.

## Terminal scenario review record

For a terminal review of new or changed scenario intent, keep a `### Terminal scenario review` entry in the batch's implementation handoff:

1. Before requesting review, identify the exact batch and each feature path relative to the repository root, with scenario IDs and source locations where IDs are missing or duplicated. Calculate SHA-256 over the raw bytes of each current complete feature file, including uncommitted changes; record each path and digest as a **pending** review. Present the exact feature changes and batch with the request. A Git commit alone may omit working-tree changes; a digest identifies content but is not an approval.
2. End the turn for explicit review under the shared contract. Do not mark pending as accepted because the user requested the work, remained silent or approved flows. If rejected or changed, keep the decision truthful, update the batch and request review of the new content.
3. On the next turn after the user explicitly approves that exact batch, recalculate each file's digest. If paths, identities, batch or any bytes differ, do not record acceptance for the changed files: present the current batch for a new decision. Otherwise record the manual acceptance, the actual date, established reviewer identity if known (otherwise `identity not recorded`), and a reference to the decision if available. Do not invent a reviewer, response or timestamp. Record before beginning implementation or other independent work, and preserve unrelated batch records. If the session ends before the decision is recorded and its evidence cannot be recovered, a new session must request review of the current batch.
4. On a later terminal session, recover the recorded explicit decision, batch and file digests; recompute all digests from the current workspace and check that paths and scenario identities still match. Reuse a matching record without re-asking. Missing, pending, ambiguous or mismatched records do not establish approval; obtain the applicable decision while continuing independent work. A record is an honest account of the manual decision, not cryptographic proof of who approved it, permission to mutate live data, or a test result. Do not claim acceptance from a digest alone.

Use the host's available SHA-256 utility, such as PowerShell `Get-FileHash -Algorithm SHA256 -LiteralPath <feature-path>` or a byte-preserving equivalent. Do not print credentials or unrelated file contents. No commit, reset or change to `.feature` files is required to record the decision.
