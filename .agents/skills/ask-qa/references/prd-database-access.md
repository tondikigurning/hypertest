# Terminal PRD database access

PRDs are shared by all clients using the configured PostgreSQL database. Configure `DATABASE_URL` as for the API; no browser identity is needed. If access is unavailable, report the blocker instead of creating a repository PRD.

From the repository root, `node server/modules/agent/prd-cli.mjs read docs/prd/<module>/<menu>.md` reads one. `list`, `versions`, `write`, and `delete` use the same shared menu records. These paths are virtual identifiers. `write <identifier>` reads a JSON object from stdin with `content` and `expected` (the exact previously read content, or null if absent). It rejects stale changes. A draft must preserve unchanged validations and leave new or changed items without `[validated]`.

For terminal flow-confirmation source comparisons, hash the exact UTF-8 output of `prd-cli.mjs read` as bytes. The identifier is not a physical file: `Get-FileHash` applies to workspace feature files, not this virtual PRD. Preserve the read bytes without adding or normalizing a newline, and hash the actual active content again after the user's decision and when resuming. A digest identifies content; it does not grant review approval. Never print the PRD when it contains material that should not enter the terminal transcript.

For version-aware access, `node server/modules/agent/prd-cli.mjs versions <identifier>` returns each version's ID, content and active state. `delete <identifier>` reads JSON from stdin with `versionId` and `expectedContent`, the exact content returned for that version. It rejects stale content and cannot delete the active version while other versions exist. Delete only the specific version explicitly requested by the user; never delete versions as routine PRD writing, workspace cleanup or to make another operation work. Deleting the sole active version removes the active PRD from list/read, while retaining the database's version state. Use the UI to activate a different version when needed; do not delete other versions merely to remove the current one.

Present the complete saved draft for explicit review. After the user accepts the exact proposed content with validations, provide `approvedSha256` in the write JSON as the SHA-256 of that exact UTF-8 content. This value records the human decision in the agent workflow; calculating a hash, a create request, or silence is not approval. The write fails if approval is required and the digest does not match. Preserve the existing review gate and reviewer metadata. Do not write PRD contents to the repository.

In that same review request, identify the saved unvalidated version and show the complete intended accepted representation, including the proposed validation tags and truthful review metadata. Hash and write that accepted representation, not the earlier unvalidated bytes. If the final representation changes before acceptance or saving, present the updated exact content for its applicable review; do not invent unknown metadata or treat a digest of one representation as acceptance of another. Save the proposal/reference and decision context needed to resume this review in another session.

If an agent update to a PRD would remove or change an existing validated line, the database requires approval before saving it even as a proposal. Present the exact proposed content first, obtain the explicit scoped decision, then write with its digest; retain the existing document if the decision is absent or rejected.
