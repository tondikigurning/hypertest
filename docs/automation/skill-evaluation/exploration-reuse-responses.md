## Contradictions and ambiguities encountered

1. **Terminal PRD review content and digest need careful interpretation.** `write-prd` Step 6 and the workflow table require a saved proposal with changed items unvalidated, followed by acceptance and agreed validations. `prd-database-access.md` says the user accepts the exact proposed content “with validations” and hashes that exact UTF-8 content. It is not completely explicit how the unvalidated saved version, displayed final validation tags/review metadata and accepted-content digest are presented together. Case 20 should show the complete exact intended accepted representation as well as identify the saved unvalidated draft, and never treat a digest of one representation as approval for different content. This is a presentation/provenance ambiguity, not permission to bypass explicit review.
2. **Terminal flow confirmation has less durable decision structure than terminal scenario acceptance.** The contract requires explicit confirmation tied to PRD/feature contents, and `flow-registry.md` permits reusing an evidenced confirmation, but it prescribes no counterpart to the exact terminal scenario decision/hash record. In Cases 18–19, no confirmation exists and the gate is clear. On saving a later confirmation, retain its actual scope, source references and decision reference truthfully in the handoff so future reuse can be assessed; do not infer it solely from a list of proposed flows.
3. **“No browser calls” versus browser cleanup is a small wording tension.** The reuse contract says to continue without browser calls when evidence suffices, while its lifetime guidance says to close an owned terminal browser when browser work is finished and Q-Rex closes after the turn. I interpret the former as no evidence-gathering/setup calls or replay, while preserving appropriate owned-session cleanup. Case 18 does not need navigation, a snapshot, login or help rechecking.
4. **A PRD can hold either requirements or prior factual evidence.** The table saying “only PRD/spec text” is unverified could be read too broadly, but the same references explicitly allow legacy PRD notes and linked dated prior observations. These are consistent when assessed by provenance: a requirement statement alone does not establish an attempt; a factual dated observation can. Case 23 recovers historical observations but the different target still requires applicability checks.
5. **Unspecified host decision modes remain unspecified.** Cases 19, 21 and 23 provide no Allow all decision. The skills correctly require the actual configured mode; their general action requests do not establish automatic acceptance. Responses above retain the native gates and describe the automatic branch only conditionally.

No instruction requires a full exploration replay merely because the phase/session changes, a registry is absent, a browser is closed/unavailable, observations are old, or the UI build is unknown. The changed target in Case 23 and explicit post-deployment delete request in Case 20 are concrete reasons for affected fresh evidence; the missing Save locator in Case 21 is a narrow evidence gap. These distinctions are explicit across the snapshot's reuse contract and specialist skills.
